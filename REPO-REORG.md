# Реорганизация репозитория ejudge (резюме сессии)

Дата: 2026-11-11

## Принятое решение

Выбран **вариант A**: интеграционная ветка + тематические ветки.

- `sch179/next` — интеграционная ветка, собранная из `v3.14.0` и тематических веток.
- `topic/*` — отдельные ветки под каждый патч/тему.
- `v3.14-sch179` — старая монолитная ветка, остаётся как legacy/точка отката; новые изменения в неё не вносить.
- fastEjudge становится основным в `dkirienko/ejudge` (`style/fastejudge.*`), браузерное расширение архивируется.

Кодовая часть `sch179/next` проверена: совпадает с `v3.14-sch179`; отличие — только добавленные документы `REPO-REORG.md`, `DOWNSTREAM.md`, `FASTEJUDGE-TODO.md`.

## Вариант A — интеграционная ветка + тематические ветки (выбран и реализован)

Структура:

- `upstream/*` — только зеркало upstream, без локальных коммитов.
- `sch179/next` — интеграционная ветка: upstream-тег + набор тематических веток; только merge/rebase, сборка, тесты, релизные теги.
- `topic/*` — по одной теме на ветку:
  - `topic/problem-dir-variants`;
  - `topic/fastejudge`;
  - `topic/school-179`;
  - `topic/daily-statistics`;
  - `topic/ok-displayed-runs`;
  - `topic/downstream-docs`.

Релиз — тег на `sch179/next`, например `v3.15-sch179-1`. Опубликованные теги не переписывать.

Плюсы:

- понятное происхождение каждого патча;
- можно обновлять upstream, перенося только нужные темы;
- легко удалить патч после принятия в upstream;
- сохраняется авторство Шашкова и наших патчей.

Минусы:

- нужно поддерживать несколько веток;
- при конфликтах всё равно требуется ручное разрешение.

## Вариант B — очередь патчей (quilt / stgit / format-patch + am)

Все локальные изменения хранятся как серия патчей в `patches/<release>/` с файлом `series` или в stgit-стеке.

Плюсы:

- явный порядок патчей;
- просто временно отключать/переупорядочивать патчи;
- удобно для upstream-ревью.

Минусы:

- больше ручной работы;
- хуже видна история и авторство;
- дублирование с git-коммитами.

Вводить, если патчей станет много и понадобится часто менять их порядок.

## Вариант C — одна долгоживущая downstream-ветка (старая схема)

Все патчи лежали в `v3.14-sch179` и переносились вручную при обновлении.

Плюсы:

- минимум действий сейчас;
- всё в одном месте.

Минусы:

- история смешивает принятые и непринятые патчи;
- сложно понять, что уже есть в upstream;
- обновление версии превращается в большой конфликтный merge;
- риск потерять авторство и происхождение патчей.

Не рекомендуется как долгосрочная модель. Ветка сохранена только для совместимости.

## Метаданные патчей

Для каждого импортированного патча фиксировать:

```text
Origin: ShashkovS/ejudge branch new_problem_dir_logic_and_ui
Origin-Commit: 8232887e4
Upstream-Status: pending | accepted | local | obsolete
```

Статус и владелец каждого патча ведутся в `DOWNSTREAM.md`.

При обновлении upstream проверять принятые патчи через `git log --cherry-pick` / `git cherry` / `git range-diff`.

## Порядок обновления upstream

```bash
git fetch --all --tags
git switch -c sch179/3.15 upstream/3.15
git merge topic/school-179 topic/daily-statistics topic/ok-displayed-runs \
          topic/problem-dir-variants topic/fastejudge
# либо git cherry-pick / git am
make && тесты
git tag v3.15-sch179-1
```

Полезные инструменты:

- `git rerere` — повторное использование разрешений конфликтов;
- `git range-diff` — сравнение старой и новой серии патчей;
- `git worktree` — отдельные каталоги для сборки разных версий;
- `git cherry` — поиск уже принятых в upstream коммитов.

## Отдельно про fastEjudge

Решение: **канонический источник — этот репозиторий**, файлы `style/fastejudge.js` и `style/fastejudge.css`.

- Браузерное расширение архивируется, новые правки в него не вносятся.
- Все изменения fastEjudge идут через `topic/fastejudge` и затем merge в `sch179/next`.
- Желательно разделить код на:
  - ядро UI (диффы, комментарии, кнопки);
  - адаптер ejudge (URL, actions, локали, заголовки таблиц).

Подробный список доработок — в `FASTEJUDGE-TODO.md`.
